========== REVISION 3 — a broken upgrade that Helm calls a success ==========

Upgrading to an image tag that does not exist. Note there is no --wait here,
which is how most upgrade commands are actually written.

$ helm upgrade checkout ./checkout-api --namespace helm-lab --set replicaCount=3 --set appVersion=v3-broken --set image.tag=v9-does-not-exist --set config.greeting=checkout-api v3 --set config.featureFlags=checkout_v2=on
Release "checkout" has been upgraded. Happy Helming!
NAME: checkout
LAST DEPLOYED: Sat Aug  1 23:55:47 2026
NAMESPACE: helm-lab
STATUS: deployed
REVISION: 3
TEST SUITE: None

Helm reports the release as deployed. (--output json also embeds the whole
rendered manifest, so filter to .info or the answer is buried in 3 KB of YAML.)

$ sh -c helm status checkout -n helm-lab --output json | jq '.info | {status, description, last_deployed}'
{
  "status": "deployed",
  "description": "Upgrade complete",
  "last_deployed": "2026-08-01T23:55:47.889386369-06:00"
}

The cluster disagrees:

$ kubectl get pods -n helm-lab -o custom-columns=NAME:.metadata.name,READY:.status.containerStatuses[0].ready,STATE:.status.containerStatuses[0].state.waiting.reason,IMAGE:.spec.containers[0].image
NAME                                     READY   STATE               IMAGE
checkout-checkout-api-586c467898-6287g   true    <none>              slo-demo:v1
checkout-checkout-api-586c467898-jhtp8   true    <none>              slo-demo:v1
checkout-checkout-api-586c467898-tnp7f   true    <none>              slo-demo:v1
checkout-checkout-api-76f65f9646-bs2qs   false   ErrImageNeverPull   slo-demo:v9-does-not-exist

Old pods are still serving because a Deployment will not tear down healthy
replicas for a rollout that never becomes Ready — this is a partial outage,
not a total one, which is exactly why it is easy to miss:
{"ok":true,"took_ms":87,"version":"v2"}


========== helm history — what is available to roll back to ==========

Watch the APP VERSION column: it reads v1 on every row, because it comes from
Chart.yaml's appVersion — NOT from the .Values.appVersion overridden with --set.
The history gives no hint that revision 3 shipped a different image.

========== helm history after the rollback ==========

Note the rollback did not RESTORE revision 2; it created revision 4 whose
content equals revision 2. Helm history is append-only, so 'roll back to the
last good one' means finding it, not decrementing a number.

$ helm history checkout -n helm-lab

========== --atomic — the flag that would have prevented revision 3 ==========

Same broken upgrade, this time with --atomic. Helm waits for readiness and
rolls back automatically when it does not arrive.

$ helm upgrade checkout ./checkout-api --namespace helm-lab --set replicaCount=3 --set appVersion=v5-broken --set image.tag=v9-does-not-exist --atomic --timeout 90s
Error: UPGRADE FAILED: release checkout failed, and has been rolled back due to atomic being set: context deadline exceeded
