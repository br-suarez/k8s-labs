========== CASE A — a report job that takes far too long ==========

Symptom: writing 200,000 rows takes seconds. The code is a plain loop over
f.write(). Nothing in the Python looks expensive.

$ python3 /work/report_writer.py --mode=slow --rows=200000 --out=/tmp/slow.csv
mode=slow rows=200000 bytes=6155780 elapsed=2.382s

Step 1 — count syscalls. 'strace -c' summarises instead of printing every call,
which is the only usable form on a process making millions of them.

$ strace -c -f python3 /work/report_writer.py --mode=slow --rows=200000 --out=/tmp/slow.csv 2>&1 | sed -n '/% time/,$p' | head -9
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 99.62    6.292214          31    200001           write
  0.12    0.007660          31       245        24 newfstatat
  0.06    0.003545          59        60         8 openat
  0.04    0.002400          35        68           read
  0.03    0.001973          28        69         2 lseek
  0.03    0.001773          26        66           rt_sigaction
  0.02    0.001557          29        52           close

200,000 write() calls for 200,000 rows — one syscall per line. Each one is a
user->kernel transition. The fix is not faster code, it is fewer crossings:
remove the per-line flush and let the runtime buffer.

$ strace -c -f python3 /work/report_writer.py --mode=fast --rows=200000 --out=/tmp/fast.csv 2>&1 | sed -n '/% time/,$p' | head -9

Identical output, different syscall count:

========== CASE B — a service that starts and then hangs ==========

Symptom: it logs 'ready' and stops. No CPU, no error, no exit.

$ nohup python3 /work/stuck_service.py > /tmp/stuck.log 2>&1 & echo $! > /tmp/stuck.pid; sleep 3; cat /tmp/stuck.log; echo "pid: $(cat /tmp/stuck.pid)"
starting order processor
connecting to upstream order feed
ready
pid: 64

Step 1 — is it running, and is it using CPU?

$ ps -o pid,stat,%cpu,%mem,etime,cmd -p $(cat /tmp/stuck.pid)
    PID STAT %CPU %MEM     ELAPSED CMD
     64 S     0.0  0.0       00:03 python3 /work/stuck_service.py

State S with 0% CPU: sleeping in a syscall. Not spinning, not crashed.
Step 2 — which syscall? /proc/PID/syscall answers without attaching:
the first field is the syscall NUMBER, the rest are its arguments.

$ PID=$(cat /tmp/stuck.pid); echo "syscall: $(cat /proc/$PID/syscall)"; echo "wchan:   $(cat /proc/$PID/wchan)"; echo; echo 'syscall 257 on x86-64 = openat'; grep -m1 ' 257 ' /usr/include/asm/unistd_64.h 2>/dev/null || true
syscall: 257 0xffffff9c 0x7fc9de62c8d0 0x80000 0x0 0x0 0x0 0x7ffd66172a40 0x7fc9de9d1011
wchan:   wait_for_partner

syscall 257 on x86-64 = openat

Step 3 — strace confirms it, and shows the call as unfinished because the
process is parked inside it rather than passing through it:

$ PID=$(cat /tmp/stuck.pid); timeout 5 strace -p $PID 2>&1 | head -6
strace: Process 64 attached
openat(AT_FDCWD, "/tmp/orders.fifo", O_RDONLY|O_CLOEXECstrace: Process 64 detached
 <detached ...>

Step 4 — which FILE is it opening? /proc/PID/fd lists what it already holds:

$ PID=$(cat /tmp/stuck.pid); ls -l /proc/$PID/fd/; echo '--- cwd ---'; ls -l /proc/$PID/cwd
total 0
lr-x------ 1 root root 64 Aug  2 06:50 0 -> /dev/null
l-wx------ 1 root root 64 Aug  2 06:50 1 -> /tmp/stuck.log
l-wx------ 1 root root 64 Aug  2 06:50 2 -> /tmp/stuck.log
--- cwd ---
lrwxrwxrwx 1 root root 0 Aug  2 06:50 /proc/64/cwd -> /work

Opening a FIFO for reading blocks until a writer appears, and nothing ever
writes to this one. Proof — supply a writer and the process moves on:

$ PID=$(cat /tmp/stuck.pid); echo 'order-1' > /tmp/orders.fifo; sleep 2; cat /tmp/stuck.log; kill $PID 2>/dev/null; true
starting order processor
connecting to upstream order feed
ready
processed: order-1
upstream closed

========== CASE C — a slow service that strace cannot explain ==========

Symptom: pricing 140 orders takes seconds.

$ python3 /work/pricing_engine.py --orders 140
priced 140 orders, total=16307.59, elapsed=0.930s

Step 1 — the same first move as case A: count syscalls.

$ strace -c -f python3 /work/pricing_engine.py --orders 140 2>&1 | tail -14

A few hundred syscalls, almost all interpreter startup. THIS IS THE FINDING:
the process is not waiting on the kernel at all, so it is not I/O, not the
network, and not a lock. It is burning CPU in user space, and strace is the
wrong tool from here on.

perf points at the CPython interpreter loop, which is correct and useless:
every Python function looks like _PyEval_EvalFrameDefault to a native profiler.
To go deeper the profiler has to understand Python frames.

$ python3 -c "
import cProfile, pstats, io, sys
sys.path.insert(0, '/work')
import pricing_engine as pe
pr = cProfile.Profile(); pr.enable()
for oid in range(140): pe.price_order(oid)
pr.disable()
s = io.StringIO(); pstats.Stats(pr, stream=s).sort_stats('cumulative').print_stats(6)
print(s.getvalue())
"
